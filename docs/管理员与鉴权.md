# 管理员与鉴权

> 结论先行：**本项目不做「登录功能」**。小程序用户的身份由微信云开发免费提供 ——
> 云函数里的 `cloud.getWXContext().OPENID` 由平台在调用链中自动注入，前端构造不了、
> 抓包也伪造不了。缺的不是「认证（你是谁）」，而是「授权（你能干什么）」。

---

## 一、你的 openid 从哪来

openid 是「你在**这个**小程序里的唯一标识」（同一微信号在不同小程序下 openid 不同）。

三种拿法，按推荐顺序：

### 方法 1：从小程序里问云函数要（最准，推荐）

新加的 `admin` 云函数有个 `whoami` action，任何人都能调，返回自己的 openid：

```js
// 微信开发者工具 → 调试器 → Console
wx.cloud.callFunction({
  name: 'admin',
  data: { action: 'whoami' }
}).then(r => console.log(r.result));
// → { ok: true, openid: 'ohxxxxxxxxxxxxxxxxxxxxxxxx', isAdmin: true }
```

`isAdmin: true` 就说明闸门认你了。

### 方法 2：云开发控制台 → 运营分析 → 用户访问

控制台里能看到访问用户列表，按昵称搜索后点右侧「复制 openid」。

### 方法 3：数据库里现成的 `_openid`

任何由**小程序端**创建的集合文档都带 `_openid` 字段，值就是创建者的 openid。
例如 `words`（生词本）集合里随便看一条记录的 `_openid`。

> ⚠ 注意：**控制台/云函数侧导入的数据没有 `_openid`**（那是管理员身份，不是用户）。
> 所以要看 `words` / `study_records` 这类用户数据集合，别看 `worddict`。

## 二、闸门在哪（三层）

| 层 | 位置 | 作用 |
|---|---|---|
| **云函数（真闸门）** | `seed` / `contentseed` / `setup` 的 `exports.main` 入口 | 服务端按 OPENID 判定，**不通过就一行都不执行**。前端绕过也没用。 |
| **前端隐藏（体验层）** | `settings.wxml` 的 `wx:if="{{isAdmin}}"` | 普通用户看不到「词库初始化」按钮。 |
| **页面兜底** | `seed.js` 的 `checkAdmin()` | 页面路由是公开的（可被直接跳转/分享进入），进页面再验一次，不通过显示「仅管理员可访问」。 |

### 为什么必须放在云函数

前端的一切都不可信：本地存储可改、抓包可伪造、前端代码在用户手里。
**只有云函数里的 `getWXContext().OPENID` 是可信的** —— 它由微信平台注入，
小程序端没有任何 API 能设置它。

### 只读云函数不加闸门

`worddict` / `content` / `tts` 都是只读的（数据本来就是所有用户可读的公开词库），
加闸门只会让正常用户查不到词。真正危险的只有三个能写全局共享集合的：
`seed`（删全站词库）、`contentseed`（删全站内容）、`setup`（建全局集合）。

## 三、白名单怎么存

`admin-guard.js` 同时认两个来源，任一命中即为管理员：

### 1. 内置指纹（代码里，sha256）

```js
const BUILTIN_ADMIN_FINGERPRINTS = [
  '39a680308f98e13c7a986a1cdc7f20ee0a7e47a53f7d523296f3cb84e56d8807',
];
```

- 存 **sha256(openid)** 而不是 openid 本身：仓库是公开的，而 openid 虽非密钥、却是个人标识；
  sha256 不可逆推（openid 熵约 166 bit，穷举不现实）。
- **零配置**：开发者本人天生是管理员，不依赖任何集合/环境变量是否就绪 ——
  这也解开了「建 admins 集合需要管理员，建 admins 集合本身就是管理员操作」的鸡生蛋问题。
- 改这个名单要**重新部署**相关云函数。

### 2. `admins` 集合（动态，不用重部署）

文档形如：

```json
{ "_id": "自动生成", "openid": "oxxxxx", "note": "张三", "added_at": "2026-10-28T…" }
```

加/减管理员在 `admin` 云函数里做，**立即生效，不需重新部署任何云函数**：

```js
// 授予（调用者必须已是管理员）
wx.cloud.callFunction({
  name: 'admin',
  data: { action: 'grantAdmin', openid: 'oxxxxx', note: '张三' }
});
// 撤销
wx.cloud.callFunction({ name: 'admin', data: { action: 'revokeAdmin', openid: 'oxxxxx' } });
// 查看
wx.cloud.callFunction({ name: 'admin', data: { action: 'listAdmins' } });
```

### ⚠ `admins` 集合的权限必须设对

**控制台里的选项名是「仅管理端可读写」** —— 云开发控制台**没有**「所有用户不可读写」
这个选项（那是自定义安全规则 `{ "read": false, "write": false }` 的等价描述，容易找错）。

操作路径：

```
云开发控制台 → 数据库 → 集合列表 → 点开 admins 集合 → 权限设置 → 选「仅管理端可读写」
```

- 「仅管理端可读写」= 小程序端**读写都被拒**，只有云函数（服务端 SDK）和控制台能访问。
- 云函数用**服务端 SDK** 读写，不受客户端权限限制 → 管理员功能正常。
- 客户端 SDK 完全碰不到这个集合 → 普通用户无法给自己发管理员。

> ⚠ **漏设 = 后门**。如果 `admins` 客户端可写，普通用户只要往里插一条
> `{ openid: "自己的openid" }` 就能把自己变成管理员，**绕过全部鉴权**。
>
> ⚠ **`setup` 云函数建集合 ≠ 权限正确** —— 它只能建空集合（服务端 SDK 没有
> 设权限的接口），建完**仍需在控制台手动改权限**。

### 怎么确认权限真的设对了（别靠肉眼）

集合权限是在控制台里点的，**点错了不会有任何报错**，只在真有人越权时才暴露。
所以项目里内置了一个主动自检：

```
小程序 → 设置 → 安全自检 → 检测集合权限
```

实现见 `miniprogram/services/permCheck.js`。它**必须在客户端跑**——
云函数用的是服务端 SDK，管理端永远有全权限，在云函数里查集合永远成功，测不出权限对不对。
只有小程序的客户端 SDK 会真正被权限规则拦截。

判定逻辑**按集合类型分级**（不是所有集合一个标准）：

| 集合类型 | 探测方式 | 判定 |
|---|---|---|
| **共享集合**（`admins`/`worddict`/`worddict_ielts`/`content_files`） | 读 + 写两次探测 | 读写都被拒 = ✓；可读 = 泄漏；**可写 = 严重后门**（任何人能改全站数据 / 给自己发管理员） |
| **用户私有集合**（`words`/`study_*`/`user_settings`） | 只做读探测 | 读不到 = 最理想；能读到自己 = **可接受**（官方保证「仅创建者可读写」时客户端读不到他人数据） |

> 📌 **为什么用户私有集合不做写探测**：
> ① 官方权限矩阵明确写着 —— 四种模式下**小程序端永远不能写他人创建的数据**
>    （平台按 `_openid` 强制隔离）。所以这类集合客户端能写自己那份**不是后门**。
> ② 真写进去一条脏数据会污染用户自己的生词本/学习记录，得手动清理。
> ③ 共享集合才是「客户端能写 = 全站被污染」的真后门，那几个必须探。

> ⚠ 写探测会真的尝试插入一条测试文档（带 `__mg_perm_probe` 标记）。
> 如果权限恰好是「可写」，那条文档会被写进去 —— 代码会在成功后**立刻删除**，
> 删不掉会在返回里标出文档 ID 供手动清理。
> **只对 4 个共享集合做写探测**，不会碰用户自己的数据。

也可以在开发者工具 Console 里手动跑：

```js
// 自检 admins 集合权限
wx.cloud.database().collection('admins').get()
  .then(() => console.warn('⚠ 客户端能读 admins —— 权限设错了'))
  .catch((e) => console.log('✓ 客户端读不到（正常）', e.errMsg));
```

## 三·补、所有集合的权限策略

📌 **本项目前端 0 处直连数据库**（`grep 'wx.cloud.database' miniprogram/` = 0），
所有数据都走云函数（`callCloud` 调 8 个云函数：admin/ai/content/contentseed/
seed/tts/worddict/words）。

所以**所有**集合都应该是「仅管理端可读写」—— 客户端完全不该碰到数据库：

| 集合 | 权限 | 为什么 |
|---|---|---|
| `admins` | 仅管理端可读写 | 漏设 = 普通用户能给自己发管理员，**直接绕过全部鉴权** |
| `worddict` / `worddict_ielts` | 仅管理端可读写 | 服务端读即可；客户端可写 = 任何人能改全站词库 |
| `content_files` | 仅管理端可读写 | 内容索引，服务端读即可 |
| `words` / `study_records` / `study_plans` / `wrong_questions` / `user_settings` | 仅管理端可读写 | 全是个人数据，本来也不该被别人读到 |

⚠ **不要因为「以前设成所有人可读」而去改它** —— 如果前端确实不直连，
设成「所有人可读」只是白白开一个数据泄漏面。改权限前先确认前端有没有直连：

```bash
grep -rn "wx.cloud.database" miniprogram/ --include="*.js"
```

> 若将来前端要直连读某个集合，**只把那一个**改成「所有用户可读，仅管理端可写」，
> 并在 `permCheck.js` 的 `CLIENT_READABLE` 里登记 —— 自检会按登记的期望值判定。

⚠ **导入方式会影响默认权限**：控制台导入的数据，集合权限默认是「仅创建者可读写」，
在小程序端读会返回空数组。所以导入完一定要显式确认权限。

## 四、代码结构与防漂移

云函数各自独立打包上传，运行时**无法 require 兄弟目录的文件**，所以需要鉴权的云函数
各存一份副本。为防止副本与权威源漂移：

```
scripts/lib/admin-guard.cjs        ← 权威源（改这里）
      │
      │ node .workbuddy/admin_wire.cjs --apply
      ↓
cloudfunctions/{seed,contentseed,setup,admin}/admin-guard.js   ← 副本
```

- 改完权威源必须执行 `node .workbuddy/admin_wire.cjs --apply` 重新同步。
- `node .workbuddy/admin_wire.cjs`（不带 `--apply`）只检查，会报差异并以非 0 退出。
- `node .workbuddy/_smoke_admin.cjs` 回归 54 项，含「四份副本字节一致」这条断言。

> 权威源用 `.cjs`：项目根 `package.json` 是 `"type": "module"`，而云函数目录下
> 的 `package.json` 没写 `type`（= CommonJS），所以副本在云函数里必须叫
> `admin-guard.js` 才能被 `require('./admin-guard')` 解析。

## 五、部署步骤

```bash
# 1. 同步 admin-guard 副本（改了权威源才需要）
node .workbuddy/admin_wire.cjs --apply

# 2. 部署四个云函数（一条命令即可，空格/逗号分隔）
npm run deploy:cf -- admin seed contentseed setup
#    也可以拆开：npm run deploy:cf -- admin
#    先干跑确认解析对不对（不调 CLI）：npm run deploy:cf -- admin seed --dry

# 3. 在控制台把**所有 9 个集合**的权限设为「仅管理端可读写」
#    admins / worddict / worddict_ielts / content_files
#    words / study_records / study_plans / wrong_questions / user_settings
#    （首次部署后集合可能还不存在 → 先在小程序里跑一次 setup#ensureCollections
#      或 admin#ensureCollection）
#
# 4. 验证：小程序 → 设置 → 安全自检 → 检测集合权限
#    9 个全绿 = 权限到位；有「⚠ 后门」按提示逐个改
```

> 📌 **控制台选项名是「仅管理端可读写」，没有「所有用户不可读写」这种选项** ——
> 后者是自定义安全规则 `{ "read": false, "write": false }` 的等价描述，在基础权限
> 下拉里找不到，别找错。完整路径与验证方法见第三节。
>
> 📌 **优先级**：4 个共享集合（`admins` / `worddict` / `worddict_ielts` /
> `content_files`）漏设 = 真后门，优先改；5 个用户私有集合漏设只是「自己的数据
> 客户端能看见」，风险低但也建议改（前端 0 直连，锁了不影响功能）。

> ⚠ **多个函数用空格或逗号分隔，别用斜杠**：`-- admin / seed` 里的 `/` 会被当成
> 一个叫「/」的函数名，CLI 去找 `cloudfunctions//` 的 index.js 必然报
> `cloudfunction entry file (index.js) not found`。Git Bash 还会把 `/` 自动转成
> 绝对路径（`C:/Users/.../PortableGit/`），更离谱。脚本现在会识别并跳过这类参数，
> 但拼错的函数名会**显式报错**而不是静默跳过 —— 别把报错当噪音忽略。

> ⚠ **`seed` / `contentseed` 加闸门后，控制台「云端测试」会拿到 FORBIDDEN** ——
> 这是预期的：控制台调用没有用户上下文（OPENID 为空），一律按非管理员处理
> （fail-closed，万一以后开了 HTTP 访问服务也不会漏出缺口）。**请在小程序里验证。**

## 六、还没做的（商业化时需要）

- **`ai` 云函数没有 openid 限流**：8 个云函数里只有 `words` 做了身份识别，其余 7 个全无身份、
  全无限流。任何人都能无限刷 AI 额度。`docs/商业化方案.md` 已把「额度按 openid 计」
  列为待做技术风险项 —— 复用本文这套 openid 机制即可，成本很低。
- **付费会员绑定**：真做 ¥98 考研全程卡时，需要绑定可长期识别的身份（微信推荐 unionid
  或手机号，不是自建账号密码）。届时给 `words` 云函数加一个 `unionid` 字段即可。
