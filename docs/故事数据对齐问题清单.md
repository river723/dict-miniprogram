## 一、结论先说

### 根因（已定位到三条，逐条可查证）

1. **英文与中文的段落分隔符不同**
   英文正文用**单个 `\n`** 分段，中文正文用 **`\n\n`** 分段。
   实测：篇 1 英文按 `\n` 切 = **94 段**，恰等于中文 94 段；
   按 `\n\n` 切只有 **3 段**（被压成一整块）。
   前端 `buildBilingualPairs` 只认 `\n\n` → **必须把英文的单 `\n` 提升为 `\n\n`**。

2. **混入 Markdown 场景分隔线 `---`**
   中英同位置各 7 处（篇 11 等），被 `\n\n---\n\n` 包裹。
   它会被当成一个"段落"，造成两侧段数虚高且无法对齐 → **必须过滤**。

3. **中文侧存在"每句对话一行"的排版习惯，英文侧是整段合并**
   例（篇 11，英文 1 段 ↔ 中文 5 段）：
   ```text
   英文[5]: "Is it free?" the boys asked in the first week. "It is free."
            "Then why does she do it?" "Ask her." He never told them; ...
   中文[5]: 「免费吗？」头一个星期，那几个男孩就问。
   中文[6]: 「免费。」
   中文[7]: 「那她图什么？」
   中文[8]: 「问她去。」
   中文[9]: 他一句也没跟他们讲。三十一年，...
   ```
   ⚠️ **这一条无法机械还原** —— 中文每个短句都是语法完整的句子
   （以 `。！？」` 结尾），没有可靠判据能判断哪些该合并。
   尝试过「句末标点判据」：篇 11 的 204 段里只有 4 段不合规（且都是斜体引文），
   信号不可用。

## 三、重生成时请遵守的规范

### 0. 最重要的一条：中英段落必须严格 1:1

**第 N 段英文 ↔ 第 N 段中文，语义完全对应。** 前端按**下标硬配对**，错一个后面全错位。

- ❌ 不要出现「英文 1 段 ↔ 中文拆成 5 段对话」这种不对称（篇 11 的致命伤）
- ❌ 不要在文中插入 `---` 分隔线（本篇数据里有，中英各 7 处）
- ✅ 若确需分段强调对话，请**两侧同步分段**

### 1. 段落分隔符统一为 `\n\n`

**英文和中文都必须只用一个 `\n\n`**（连续两个换行）。

- ❌ 不要用单个 `\n` 当段落分隔（篇 12 的英文就是这样，导致整篇被压成 1 段）
- ❌ 不要在段落内部再加 `\n` 做视觉折行
- ✅ 段落之间：`...end of para.\n\nStart of next...`
- ✅ **不要**在正文开头重复写标题行（标题有独立字段 `title_zh` / `title_en`）

校验方法：`(s.match(/\n\n/g) || []).length` 应等于「中英各自段数 − 1」，
且 `en_body.split(/\n\n+/).length === zh_body.split(/\n\n+/).length`。

### 2. 中英段落必须严格 1:1

第 N 段英文 ↔ 第 N 段中文，语义对应。前端按**下标硬配对**，错一个全错位。

### 3. 各篇段落数保持一致

同一篇里，英文段数必须**恰好等于**中文段数。建议每篇段落数控制在 **85–95 段**
（现有对齐篇目的自然值域）。

### 4. 其他已知的字段约定（沿用即可）

| 字段 | 要求 |
|---|---|
| `id` | 1–20，连续 |
| `title_zh` | 中文标题，非空（小程序列表/详情显示这个） |
| `title_en` | 英文标题，非空（保留备用） |
| `genre` | 中文题材名（如「庭审悬疑」），需与现有 20 个取值一致，勿临时新增 |
| `target_count` | 该篇词数，20 篇合计须 **4801** |
| `words[]` | 每项 `{w, pos, zh, tip, role, field}`；`w` 必须是词库原词 |
| `en_body` | 英文正文，**不含** `**` 粗体标记（高亮由 words 列表驱动） |
| `zh_body` | 中文正文，**不含**任何 `*` 标记 |

> ⚠️ 关于粗体：英文正文里的 `**word**` 标记本项目**不需要**——高亮完全由
> `words[]` 列表 + 正则匹配生成，写了反而要额外清洗。生成时请不要加粗。

## 四、重生成后的自检脚本

### 方式 A（推荐）：项目内置总闸门

新数据到手后，**只需这一条** —— 自动识别 anthology / chapters 两种格式，
做结构 + 渲染双重体检，通过才写出：

```bash

```

不通过会直接列出问题篇目与差值，并指向本清单；通过则输出可直接被
`content:build` 消费的 `stories.json`，并提示后续部署步骤。

### 方式 B：独立脚本（不依赖项目代码）

若在项目外核对，可用这段：

```bash
node -e "
const j = require('./新故事.json');
const paras = s => String(s).split(/\n\n+/).map(t=>t.trim()).filter(Boolean);
const pieces = j.pieces || j.chapters;
let bad = 0, words = 0;
for (const p of pieces) {
  const en = paras(p.en_body || p.content).length;
  const zh = paras(p.zh_body || p.translation).length;
  words += (p.target_count || (p.words||[]).length);
  const star = ((p.en_body||p.content||'').match(/\*/g)||[]).length +
               ((p.zh_body||p.translation||'').match(/\*/g)||[]).length;
  if (en !== zh || star) { console.log('✗', p.id, p.title_zh||p.title, 'en'+en, 'zh'+zh, star?'星号'+star:''); bad++; }
}
console.log('不齐/带星号:', bad, '| 词汇合计:', words, words===4801?'✓':'✗ 应为 4801');
"
```
