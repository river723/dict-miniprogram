## 「导入完成后还是星际漫游者」——同一现象的两个独立成因

用户连续三轮换故事集（星际漫游者 → 南苑九十天 → 烟火故事集），界面**始终是第一个**。
顺着链路 `seed.js ⑤ → contentseed#import → uploadOne → content_files 索引 → content#storyList
→ read.js#loadStories` 逐段排查，定位到两个各自独立的原因：

### 成因 A：tab 页不走 onLoad，导入后永不刷新
`read.js` 只有 `onLoad` 调 `loadStories()`；Tab 页 switching 只触发 `onShow`。
从设置页返回阅读页 → `onShow` → 列表还是旧 data。
已有 `onPullDownRefresh` → **`enablePullDownRefresh: true`（read.json 已开）可立即自愈**。

长效修法（本次已写）：
- `utils/story.js` 导出 `clearStoryCache()`（模块级 `indexCache`/`chapterCache`）
- `seed.js` 导入/清空后 `markStoryDirty()` → 写 `mg_story_dirty`
- `read.js#onShow` 见标记则 `loadStories()` 并清标记
- `read.js#onPullDownRefresh` 也 `clearStoryCache()` —— 否则章节详情页仍吃旧缓存

### 成因 B（更隐蔽）：同 cloudPath 上传很可能不替换内容
`uploadOne` 原本「先传后删索引」，依赖「同 path 自动覆盖」。
若平台对已存在 path 直接复用旧对象（返回旧 fileID），则 **文件字节从未变过**，
而 `content#readJson` 只是拿新 fileID 下载同一份旧内容 —— 完全解释了「三轮都显示第一版」。
改为**严格幂等**：`deleteFile(旧fileID) → remove(旧索引) → uploadFile(同path) → add(新索引)`。

- `verify()` 返回 `label`（系列名 / 章节标题+theme）
- 设置页新增「云端当前故事集」一行 + 「导入后在阅读页下拉刷新」提示

## 真正根因（2026-10-08 傍晚定位）：部署脚本一直「假成功」
用户第六次说「还是不行」，重跑 `info()` 云端测试，**返回里没有 `build`/`cloudStory`/`inlineSeriesTitle`**
——证明云端跑的仍是改之前的旧 `contentseed`。之前所有「部署成功 ✓」全是假的。

两个叠加 bug（都在 `scripts/deploy-cloudfunctions.mjs`）：
1. **本机 `spawnSync(cmd)` 对 cmd.exe 稳定报 `EBUSY`**（与之前 `node --check` 踩的是同一环境坑），

2. 旧 `deployOne` 成功判定 `!/\[error\]|×/.test(out)` —— 空字符串永远命中 → **空输出被误判成功**。

结果：几轮"部署"代码从没上云，云端写入逻辑一直是旧的（同 path 覆盖、不删旧文件），
新《烟火故事集》数据从没真正写进云，所以"三轮都显示第一版"的真正原因是**部署空转**，
而非读取侧缓存（缓存只是叠加因素）。

### 修法（已写并验证）
- 改用 **`exec` + 整串带引号命令**（`'"'+cli+'"' cloud ...`，shell 不重新引号化 argv），
  绕过 spawnSync 的 EBUSY 与 spawn 的 argv 引号转义坑（`"Program Files"` 路径被拆成 `C:/Program`）。
- 成功判定改为：**空输出一律判失败**；有表看 `│ true │`，无表看有无 `[error]`/`×`。
- 实测：`node scripts/deploy-cloudfunctions.mjs content contentseed` → 真实输出 `✓✓`，EXIT=0。
  ⚠️ 不要 `| head` 管道，会 SIGTERM 掐断（云函数带 `-r` 云端装依赖较慢）。

## study 页"一直加载中 + 加载中出现两次"（2026-10-08 深夜，修正）
用户反馈：加 `_inited` 守卫后，从"首张卡闪两次"变成"**一直加载中，且加载中出现两次**"。
重新定位——**守卫本身没错（它确实消灭了同期重入的"闪两次"），真正的元凶是云调用无超时**：

- study 是**普通页面**（`wx.navigateTo` 进入，见 home.js:257，非 tabBar）；`app.json` 开 `lazyCodeLoading`。
- **"加载中出现两次"的真正机制**：真机调试重连会让框架**重建一次页面**（不同实例），
  两次独立加载各显示一次 loading → 表现成"出现两次"。这是**调试器行为，app 端无法禁止**。
- **"一直加载中"的真正机制**：旧 `callCloud` 直接 `wx.cloud.callFunction` **无超时**，
  真机调试首次连接时 `worddict` 云调用（fillTodayIfNeeded 链路）经常**挂起不返回也不 reject**
  → `await fillTodayIfNeeded` 永久 pending → 永远 `loading`。
  守卫把第二次 onLoad 挡掉后，第一次那个卡住的 `load` 没人救活 → 永久卡死。

**根因 = 云调用缺超时兜底**，不是重复加载本身。

**修法**：
- `miniprogram/services/cloud.js`：`callCloud` 用 `Promise.race` 包 `withTimeout`（默认 **25000ms**，
  `opt.timeout` 可覆盖）。所有云调用（worddict/ai/content…）统一受益。
  `fillTodayIfNeeded#doFill` 的 catch 已 `return 0`（不抛）→ 超时后 `load` 照常进入（降级：本次不自动配词）。
- `study.js`：保留 `onLoad` 的 `_inited` 守卫（解决同期重入闪两次）+ `load` 的 `_loadPromise` 单飞。
- 校验：cloud.js `node --check` 通过；check_syntax 全绿。
⚠️ `cloud.js` 是**前端服务层**（封装 wx.cloud.callFunction），**不是云函数** → 只需开发者工具
**重新编译前端**，无需 `deploy:cf`。
✅ 结论：重连两次的调试机制仍在，但每次重连都会在 25s 内进入页面而不再卡死；正常预览/体验版无此问题。

## 教训（云调用专项，重要）
**小程序 `wx.cloud.callFunction` 在真机调试/弱网下可能长期不回调也不 reject**——
任何 `await` 它的链路都会永久挂起（表现：一直加载中）。**所有云调用封装必须有超时兜底**
（`Promise.race` + `setTimeout` reject）。排查"真机卡、模拟器正常"的加载问题，优先查 `callCloud` 有无超时，
而不是先怀疑页面重复渲染。

## ⚠️ 真正根因来了（2026-10-08 深夜，修正）：`.finally` 真机运行时不存在
上一节把"一直加载中"归因为云调用无超时——那是叠加因素，但**真正炸掉 `load` 的是代码自身的 API 兼容问题**。
用户贴出真机 console：
```
TypeError: a.finally is not a function
at study.js:228  (task.finally(() => { this._loadPromise = null; }))
```
- 真机（**非模拟器**）的 JS 运行时**不支持 `Promise.prototype.finally`**（ES2018）。模拟器跑现代 V8 所以有，
  真机调试引擎没有 → 这正是"模拟器正常、真机卡死"的教科书级表现。
- 第 228 行 `.finally` 在 `load()` 里**同步抛错**（`load` 是 async，异常变 rejected promise 且无人 catch），
  导致 in-flight 单飞那段清理没跑、且 `load` 整体被打断 → 永远停在 `loading:true`。
- **全项目共 6 处 `.finally`**，真机都会炸：`study.js / autoWord.js / read.js（onPullDownRefresh）/
  dictionary.js / home.js / word-list.js`。已全部替换为 `.then(cb, cb)`（语义等价：成功失败都跑副作用）。
- 教训：**真机调试遇到的"TypeError: xxx is not a function"且只在真机出现，优先怀疑 ES2018+ API
  （`.finally`、可选链 `?.`、空值合并 `??` 等）在真机引擎缺失**，而不是业务/逻辑 bug。改完须重新编译前端。

### ⚠️ 更深的坑（同一处代码第二次炸）：本工具链 async→generator 转译
`study.js#load` 最初写成「`const task = (async () => {...})(); task.then(...)`」做 in-flight 单飞。
改掉 `.finally` 换成 `.then` 后，模拟器也炸：`task.then is not a function`。
**根因**：本项目工具链把 `async` 转译为 **generator**（`_async_to_generator.js` / `_ts_generator.js`），
**嵌套的「async 箭头 IIFE」经转译后返回的是生成器对象（有 `.next`、无 `.then`/`.finally`）**，
对其调用任何 Promise 方法都会抛错。这不是运行时缺失，是转译产物的形态问题，**模拟器和真机都会炸**。

**正确写法**：不要「持有内层 async IIFE 返回的 Promise 并调用其方法」。改为——
把 `load` 写成**扁平 async 函数**，用**同步 `try/finally` 块**（语句块 finally，**不是**
`Promise.prototype.finally`）释放标志位；单飞用布尔 `this._loading` 标志（不要用 `this._loadPromise` 存 Promise）。
`await` 本身在顶层 async 函数是 OK 的，只有「内层 async 箭头 IIFE」会踩这个形态坑。

## 修复：自动配词已开却误报「词库已用尽」（2026-10-08）
现象：设置里自动配词已开，点「继续学习/学习新词」有时弹「词库已用尽，可去词库手动挑选」。
根因（两处叠加）：
1. `home.js#onAnotherGroup` 只要 `fillTodayIfNeeded` 返回 `added===0` 且开关开着，**一律**报
   "词库已用尽"。但 `added===0` 不等于「词库真空」：
   - `autoWord.js#doFill` 原 `catch` 把云函数超时/网络抖动的异常**静默吞成 return 0** →
     配词失败时也得到 added=0 → 误报"词库已用尽"（这是"有时"出现的真凶）。
   - `pick` 云函数候选池真空（`candidates===0`）才是真·用尽。
2. `fillTodayIfNeeded` 原用模块级 `inflight` 单飞，**忽略 `force` 参数** → `refresh` 的非强制调用
   若还在飞，"继续学习"的强制补充会被复用成非强制结果（added=0）而误报。
修复：
- `autoWord.js`：`doFill` 返回 `{added, exhausted}`，异常 `throw`（不再静默成 0）；
  `fillTodayIfNeeded` 始终返回数字，并新增 `getLastFillResult()` 暴露 `{exhausted, error}`；
  **去掉 inflight 单飞**（doFill 内部靠 autoFillLastDate 幂等，force 调用每次真跑）。
- `home.js#onAnotherGroup`：加 12s 局部超时兜底（避免干等 25s）；按 `getLastFillResult()` 区分
  文案：失败→"配词失败，请稍后重试"；开关关→"自动配词已关闭…"；真·用尽→"词库已用尽…"；

## 生词本「最近」排序不更新（2026-10-08 末）

修法（最小侵入，不动 created_at 日期语义避免影响别处）：

- `word-list#apply`「最近」分支改为优先按 `created_ts` 排、旧词回退 `created_at`；
  `home.js`「最近添加」预览同样改用 `created_ts` 优先。
