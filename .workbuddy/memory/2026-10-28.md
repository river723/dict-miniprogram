## 用户提问「是否应该有个登录功能来判断管理员」→ 结论：**不需要做登录功能**

关键认知（小程序与 App 的根本差异）：
- 小程序用户**已经登录了微信**，`wx.login` 走的是静默授权，用户无感。
- 云函数里 `cloud.getWXContext().OPENID` **由微信平台自动注入，前端无法伪造**，
  且项目里 `words` 云函数已经在用（按 `_openid` 隔离用户数据）→ **身份层已经免费具备了**。
- 所以**缺的从来不是「登录/认证」，而是「授权/角色」**：即「这个 OPENID 是不是管理员」。
- 真做「登录功能」（手机号+密码/验证码/昵称头像/自建账号体系）属于过度设计：
  要维护 session、要过审、要处理找回密码，还要新增隐私政策 —— 而这些解决的
  不是当前问题。微信生态里身份是**平台给的**，不是自己造的。

### 推荐方案（openid 白名单 + 前后端双锁）
1. **云函数层（安全底线，必须做）**：`seed` / `contentseed` 入口取 `OPENID`，
   不在白名单 → 直接 `return { ok:false, error:'FORBIDDEN' }`，**一行都不执行**。
   前端传的任何东西都不可信，鉴权只能在服务端。
2. **前端层（体验 + 纵深防御）**：settings 页异步取 `isAdmin`（如 `admin` 云函数
   或 `words` 加一个 `whoami` action）；非管理员隐藏「词库初始化」按钮；
   `seed` 页 `onShow` 再校验一次，不通过 `navigateBack`。
3. **白名单存哪（3 选 1）**：
   - 写死常量 `const ADMIN_OPENIDS = ['oxxxx']`（最简单，改名单要重部署云函数）
   - 云函数环境变量 `ADMIN_OPENIDS`（改不用重部署，但要控制台改）
   - 建 `admins` 集合存 openid 文档（最灵活，可多人、可随时增删；
     但集合权限要设为**仅管理员可写**，否则用户能自己把自己加进白名单 ⚠）

### ⚠️ 推送被 GitHub secret scanning 拒绝 —— 重要教训
第一次 push 报 `repository rule violations`：
```
remote: To push, remove secret from commit(s) or follow this URL to allow the secret.
remote: https://github.com/river723/dict-miniprogram/security/secret-scanning/unblock-secret/...
```
**根因**：排障时把真实腾讯云 SecretId `AKID***(已脱敏)`
写进了 `.workbuddy/memory/2026-10-27.md`（第 7 行）。

- **SecretId（AKID 开头）本身就是敏感凭证**，「只有 ID 没有 Key 危害小」是错觉 →
  一样被扫描器判定。写日志只写「已能 echo 出来」，**绝不写值本身**。
- **`.workbuddy/memory/` 是要入库的**（项目记忆靠 git 同步给后续会话），不是本地临时目录
  → 往里写东西前先想「这段会不会进公库」。
- **排查手法（一次扫全历史含远端分支）**：
  ```
  git grep -I -n -E "AKID[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{24,}" $(git rev-list --all) --
  ```
  本次据此确认**仅 1 处、且仅在未推送的提交里** → 远端历史本来就干净，
  不需要重写历史（重写会改写已推送历史，风险大得多）。
- **修法**：软重置把含密钥的提交与脱敏提交合并成一个新提交（`reset --soft` + 重新 commit），
  让含密钥的 blob 彻底不可达；再用同一 grep 复验 → 无命中。
- 已把「密钥绝不入库」写进 MEMORY.md（长期约定）。
